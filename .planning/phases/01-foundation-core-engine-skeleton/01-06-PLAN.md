<task type="checkpoint:decision" gate="blocking">
  <decision>Is `.prismdocs/project.json` — the project-id marker — committed to the user's repository, or gitignored along with the rest of `.prismdocs/`?</decision>
  <context>
This is the one decision in Phase 1 that neither CONTEXT.md nor RESEARCH.md settles, and it is a one-way door: it changes what PrismDocs puts into the user's git history, and reversing it after users have projects means re-associating orphaned data by hand.

The marker is how a project survives being moved or renamed (D-13) — plan 01-03's resolver reads it first and treats it as authoritative. D-19 says `.prismdocs/` gets a `.gitignore` suggestion (PRD §4.1), but that suggestion predates the marker, whose form was left to the planner.

The file contains one random UUID, a timestamp, and a schema number. No secrets, no comments, no document content. But PrismDocs' central promise to the user is that their repository stays clean, so adding even one tracked file is a decision the user should make rather than discover.

RESEARCH assumption A3 recommends committing it and flags it as "worth confirming with the user."

**What this decision does NOT control.** Backup and restore work either way. Plan 01-03's export writes a `manifest.json` naming the `project_id` INTO the archive, and its resolver adopts an unclaimed restored data directory before minting a new id, so a restore succeeds with no marker and no registry row (`restore_from_archive_adopts_manifest_project_id`). NFR-02's promise is therefore already unconditional and is not riding on this answer. What remains genuinely at stake is narrower: whether a plain `git clone` — with no backup archive involved — arrives already knowing which project it is.
  </context>
  <options>
    <option id="commit-marker">
      <name>Commit the marker (gitignore `.prismdocs/*` with an exemption for `project.json`)</name>
      <pros>A `git clone` on a second machine re-associates to the same project id instead of minting a fresh one and orphaning the first machine's data. Makes the identity durable against a deleted app-support directory. Recommended by RESEARCH A3.</pros>
      <cons>Adds one tracked file to the user's repository, which is a visible dent in "your repo stays clean". Teammates who clone the repo inherit the same project id, which is harmless today but is a shared identifier the design has not yet reasoned about for multi-user (V2-04).</cons>
    </option>
    <option id="ignore-marker">
      <name>Gitignore the marker with the rest of `.prismdocs/`</name>
      <pros>Nothing PrismDocs creates is ever tracked; the promise holds absolutely. No shared identifier leaks into a team repo.</pros>
      <cons>A plain clone on a second machine mints a new project id, so the two machines never share project data, and moving the work across machines requires exporting a backup rather than just cloning. Restoring that export still works — plan 01-03's archive manifest re-associates it with no marker present — so this costs a step, not the data.</cons>
    </option>
    <option id="ask-per-project">
      <name>Ask the user during onboarding step 3, defaulting to committing</name>
      <pros>No global assumption; the user with a shared team repo and the user with a private one each get what they want.</pros>
      <cons>One more onboarding question in a flow that is already four steps, for a decision most users have no basis to make on first run.</cons>
    </option>
  </options>
  <resume-signal>Select: commit-marker, ignore-marker, or ask-per-project</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → user's git repository | PrismDocs writes files into a directory the user version-controls and shares |
| app → user's existing `.gitignore` and `.mcp.json` | Pre-existing files the user owns are modified |
| keychain → helper script → MCP client | The token travels from OS storage to a client at connect time |
| user-chosen directory → enumeration | An arbitrary tree, possibly containing symlinks, is walked |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-09 | Information disclosure | Token written into a committed `.mcp.json` | high | mitigate | The credential is resolved at connect time by a helper script that reads the keychain; the token value never appears in the generated file. Enforced by `mcp_json_contains_no_token` and by the manual `git diff` check. |
| T-1-11 | Tampering | Symlink escape during enumeration | medium | mitigate | Canonicalize the workspace root and refuse to follow a link out of it. Enforced by `enumeration_stays_within_canonical_root`. |
| T-1-18 | Tampering | Clobbering the user's `.gitignore` or `.mcp.json` | medium | mitigate | Append-only for `.gitignore` and only with explicit consent; merge-by-key for `.mcp.json` preserving unrelated entries. Enforced by `prismdocs_gitignore_requires_consent` and `mcp_json_merge_preserves_other_servers`. |
| T-1-19 | Tampering | Injection into generated files | low | mitigate | `.mcp.json` is produced with `serde_json` and the README and snippet from templates; no user-controlled string is concatenated into markup or JSON. |
| T-1-01 | Spoofing / Elevation | The generated config points at a live loopback server | high | mitigate | Verified end to end by the manual check: a real client connects, and a foreign-Origin request is still refused with 403 and logged. |
