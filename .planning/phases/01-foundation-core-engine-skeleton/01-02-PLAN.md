Output: an app you can launch, configure, and watch successfully talk to a real endpoint, with the result persisted in a real WAL database.

<assumption_delta_decision>
**Trigger:** the `chosen` signal on "the user configures an LLM endpoint with a custom `base_url`" — the provider endpoint moved from a constant to a user-supplied parameter, and D-15 requires two provider *families* at launch. Per the checkpoint: has a configuration decision become a modeling decision?

**Yes.** The generalized identity is no longer "the Anthropic API" and no longer "an api_key" — it is a **provider profile**.

- **Primary noun:** `ProviderProfile` — `{ id, family: ProviderFamily, base_url: Url, secret_account: String, default_model: Option<String>, created_at }`, persisted as a first-class row in `llm_provider_profiles`.
- **Decision: `promote`.** `ProviderProfile` becomes the primary identity every call site takes; `ProviderFamily` (`Anthropic` | `OpenAiCompatible`) is **demoted to a variant field on it**, and the two `LlmProvider` implementations are selected from that field at runtime. There is no "the Anthropic client" singleton and no `Option<base_url>` overlaying a default constant.
- **Rationale:** adding the second family alongside a still-privileged first one would make the endpoint a per-provider special case, and Phase 4's deferred multi-model routing (Q1: cheap model for bulk, strong model for decision paragraphs) would then need a schema change rather than a second row. Promotion also keeps D-05 honest — swapping the hand-rolled Anthropic client for a Node sidecar replaces one `impl LlmProvider`, and no caller notices.
- **Not accepted debt:** this is a promote, not an add-alongside, so there is nothing to pay back later.

**Companion invariant test (accepted, added as Task 2 work):** `provider_profile_is_family_agnostic` in `crates/prism-llm/tests/provider_probe.rs` iterates every `ProviderFamily` variant, constructs a client from a `ProviderProfile` alone, and asserts each produces its family's correct auth header against the mock endpoint. It goes red the moment a future phase reintroduces a hard-coded single provider or a family-specific call path.
</assumption_delta_decision>

**`prism-core` — the facade and its trait split (D-02/D-03).** Define `WorkspaceId`, `ProjectId`, and an `EngineError` enum built with `thiserror`. Define the three op traits that partition the write surface in `ops.rs`: `ReadOps` (available to both doors, every method workspace-scoped), `AgentWriteOps` (the COMPLETE agent write surface — in Phase 1 it is declared with the `respond_to_comment` signature only, whose body returns an unimplemented-in-this-phase error since comments arrive in Phase 4/5), and `AppWriteOps` (app-only writes). `prism-mcp` will be generic over `ReadOps + AgentWriteOps` in plan 01-05 — declaring the split HERE is what makes AGENT-03's write limit a compile-time property rather than a runtime check. `Engine` holds the `r2d2` pool, a `Box<dyn SecretStore>`, and the provider registry, and is constructed from an INJECTED base directory — `prism-core` must never call Tauri's `app_data_dir()` (Pitfall 6), because that would require an `AppHandle` and make the core untestable headless.

**`prism-store` — real WAL pool, real migration, real write.** Build the `r2d2` pool over `SqliteConnectionManager` with a connection customizer that runs, per connection: `journal_mode` set to WAL via `pragma_update_and_check` (the plain `pragma_update` fails because this pragma returns a row), `synchronous` set to NORMAL, `foreign_keys` on, and a 5-second `busy_timeout`. Do NOT hold an `Arc<Mutex<Connection>>` — that satisfies D-02's wording and silently defeats D-14 (Pitfall 1). Wrap every store call reachable from async in `tokio::task::spawn_blocking` INSIDE the store crate so the discipline cannot be forgotten at a call site (Pitfall 8). Write the INSTALL-level migration set (`app` migration 001) as a const `M::up` slice applied with `to_latest()`, creating exactly three tables and nothing more (PA-5): `workspaces` (the registry — project_id TEXT PK, root_path TEXT, display_name TEXT, created_at, last_opened_at), `settings` (install-scoped key/value), and `llm_provider_profiles` (id TEXT PK, family, base_url, secret_account, default_model, created_at).
