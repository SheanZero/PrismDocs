Create `docs/adr/README.md` establishing the convention: numbered records, `NNNN-kebab-title.md`, each with Status, Context, Decision, Consequences, and Alternatives Considered, and a one-line index. Then write `docs/adr/0001-tauri-vs-node-sidecar.md` with status Accepted and today's date.

**Decision.** Tauri v2 shell with a Rust-centric core, and everything that could plausibly have been a Node sidecar kept in Rust: `rmcp` for MCP, `async-openai` for OpenAI-compatible endpoints, and a thin hand-rolled `reqwest` client for Anthropic. State the reasoning as it actually is: zero Node runtime shipped, the smallest bundle, a single toolchain, and the API key never leaving the Rust process.

**The rejected alternative, stated fairly.** A bundled Node sidecar hosting both the MCP server on `@modelcontextprotocol/sdk` and the LLM clients on the official Anthropic and OpenAI SDKs. Give it its real advantages — those SDKs are the most battle-tested, they handle SSE edge cases and exact token counting better than hand-rolled code, and Claude Code itself is built on the TypeScript SDK — and its real cost, roughly 40 to 80 MB of Node runtime plus an IPC hop between the Rust core and the sidecar. A rejected option written as a straw man is worthless to the person who later has to reconsider it.

**The downgrade trigger (D-05).** This is the part that makes the ADR useful rather than decorative, so make it concrete and testable: the Anthropic client is isolated behind the `LlmProvider` trait, and the trigger to swap its implementation for a Node sidecar is hand-rolled SSE handling proving unreliable in practice — specifically, streaming edge cases that cost more to fix than the sidecar costs to ship, or a need for exact Anthropic token counting that the REST endpoint cannot serve. Name what would change if triggered: one trait implementation, and no caller.

**Consequences and recorded deviations.** Include, each with its reason: the MCP transport is app-hosted loopback streamable HTTP rather than stdio, overriding the stack doc's earlier description, because AGENT-03's wording requires Origin semantics that a stdio pipe cannot carry and because the app is itself the server with no subprocess. The app-support directory is the human-readable product name rather than Tauri's reverse-DNS bundle identifier, because it is a user-visible backup location under D-12, and the core never calls Tauri's path API regardless since that would require an app handle and break the headless-core rule. The Engine facade holds a connection pool rather than a literally shared database handle — a deviation from D-14's wording that serves D-14's intent, since `rusqlite`'s connection type is not `Sync` and the obvious mutex-wrapped alternative serializes reads behind writes and cancels WAL's whole benefit. Note that the MCP protocol revision pin is satisfied by construction rather than by configuration.

**Accepted risk.** Record SSRF via user-supplied `base_url` as knowingly accepted: NFR-04 requires arbitrary endpoints for proxies and local models, so blocking it would break the requirement. State the blast-radius controls applied instead — an http/https-only scheme allowlist and the destination host shown in the UI — and say plainly that this is a deliberate trade, not an oversight.

**The project-marker decision.** Record the outcome of plan 01-06's `checkpoint:decision` — whether `.prismdocs/project.json` is committed to the user's repository or gitignored with the rest of `.prismdocs/` — as a section of its own, with the option chosen, the reason the user gave, and the consequence for a `git clone` on a second machine. This plan runs in a wave after 01-06 for exactly this reason: it is the only genuinely open one-way door in the phase, every other decision was settled in CONTEXT.md or by RESEARCH, and SC-5 asks for the architecture decisions to be recorded rather than for most of them. If the SUMMARY does not carry a resolution, stop and say so rather than writing the ADR around the hole.

Reference the planner assumptions PA-1 through PA-6 rather than restating them.

Create `.github/workflows/ci.yml` triggered on push and pull request, with two jobs on `macos-latest` (arm64, matching the target platform per PA-6).

The `core` job is the fast gate and deliberately installs NO Node and builds NO webview: check out, install the pinned 1.95 toolchain with clippy and rustfmt, restore a Rust cache, then run in order — a formatting check across the workspace, clippy over the four core crates with all targets and warnings denied, the test suite for those four crates, and `cargo tree -d` filtered for a duplicate `libsqlite3-sys` or `reqwest v`. Use the same unanchored pattern plan 01-01 uses (`libsqlite3-sys|reqwest v`), never a start-of-line anchor: `cargo tree` indents children with box-drawing prefixes, so an anchored match sees only an unindented duplicate root and passes vacuously on a nested one. This job's constitution is the point: the day `cargo test -p prism-store` needs a webview to run, this job breaks and tells you the boundary D-01 established has leaked. Add a comment in the workflow saying exactly that, so nobody later "fixes" it by adding a Node setup step.

The `shell` job is the slower gate: same runner and toolchain, plus Node setup, `npm ci`, and a debug Tauri build. Let it depend on `core` so a boundary violation fails fast and cheap.

Exclude the real-keychain integration test from the `core` job — it is marked ignored precisely so a headless runner never blocks on a Keychain prompt. Note in a comment that it is run locally and belongs in a future nightly job rather than being deleted.

Keep every command byte-identical to what `01-VALIDATION.md` records as the quick and full suite commands, so a developer running the local gate and CI running the remote gate cannot disagree about what green means.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner → crates.io and npm | Dependency resolution and C-compiling build scripts execute on a hosted runner |
| CI runner → keychain | A headless runner has no usable Keychain and must not be asked for one |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-SC | Tampering | Dependency resolution on the CI runner | high | mitigate | A committed root `Cargo.lock` plus a pinned toolchain make CI resolution reproducible; `cargo tree -d` fails the build on a duplicate native-library crate. All crates carry an OK verdict in `01-RESEARCH.md` § Package Legitimacy Audit, so no blocking legitimacy checkpoint applies. |
| T-1-06 | Information disclosure | Egress sprawl reintroduced later | medium | mitigate | The `core` job runs the `single_egress_path` and `no_telemetry_dependency` assertions on every commit, so a second HTTP client or an analytics dependency fails CI rather than shipping. |
