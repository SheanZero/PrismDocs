<objective>
关闭本轮评审在 prism-mcp 门禁层的三条：

- **本轮 WR-05（≡ 上轮 WR-15）**：`constant_time_eq` 在第 151 行早退之后，第 158 行的 `expected.len().max(1)` 永远取不到 `1` 那一臂，第 163-168 行整段死代码，而它的注释描述了一个函数进不去的状态。在一个「靠人读一遍就能验证」的函数里，一段为不存在的第二条空值路径写的注释是**主动的危险**：下一个读者可能删掉第 151 行的守卫，以为 163-168 覆盖了那个情况——它们不覆盖，删掉之后 `constant_time_eq("", "")` 重新返回 true，CR-03 原样复活。
- **本轮 WR-06**：`McpDeps::new` 用 `bearer.trim().is_empty()` 判空却存**未 trim** 的原值。`McpDeps::new(.., "0123abcd\n")` 构造成功，而 HTTP 头解析会剥掉呈递值的尾随 OWS，于是那个换行永远比不中——**每一个**请求都被拒，且拒绝形态与伪造 token 完全相同（`warn!("bearer token mismatch")`）。Phase 6 从钥匙串读 token，而钥匙串往返、文件回退、`Command` 输出都常带尾随换行。
- **本轮 WR-07**：`raw.strip_prefix("Bearer ")` 是字节精确匹配。RFC 7235 §2.1 定义 `auth-scheme` 为大小写不敏感 token，RFC 6750 的客户端合法地发 `bearer` / `BEARER`；同一行也拒掉了 scheme 与 credentials 之间的多个空格。在一个客户端不受本项目控制的集成里（Phase 6 的 Claude Code 与其他 agent），一个合规客户端与一次攻击在这条门禁前完全同形。

Purpose: 三条都是「门禁本身是对的，但它在正确输入上误拒、或它的可读性正在邀请一次 fail-open 回归」。现在改的成本是零，Phase 6 接上真 token 之后诊断成本极高。

Output: 一个只有一个空值处理点、对合规客户端不误拒、且存取同一份归一化字节的 bearer 门禁。
</objective>
