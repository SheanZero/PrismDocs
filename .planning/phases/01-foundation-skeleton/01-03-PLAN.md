  <options>
    <option id="option-a">
      <name>方案 A：external content FTS + `documents.rowid_pk INTEGER PRIMARY KEY` + 三触发器 + 全粒度索引（`detail` 不声明，取默认 full）+ STRICT 表（研究推荐）</name>
      <pros>
        全粒度索引保住 >3 字符的 MATCH 查询——D-01 的 4 字中文词能搜到（这正是 external content
        省下来的体积让「不为省体积而降粒度」变得没有代价）；
        内容只存一份（trigram 索引本身已约 3× 体积，普通表会再翻一倍）；
        三触发器由数据库强制索引同步，Phase 2/3/5 新增的写路径不可能「忘记」同步；
        支持 `rebuild` 命令（contentless 表不支持，Phase 2+ 重建索引是可预期需求）；
        显式 `INTEGER PRIMARY KEY` 规避 `VACUUM` 重编号 rowid 导致索引与内容表静默错位；
        STRICT 让类型错误在写入时报错而不是静默转换。
      </pros>
      <cons>
        schema 更复杂（三个触发器 + 一个代理主键列 + 一个 ULID 唯一列）；
        STRICT 在 Phase 2/3 若出现动态列需求需要一次 ALTER-free 的表重建；
        触发器逻辑出错时表现为「搜不到」而非报错，需要 plan 01-05 的触发器同步测试兜住。
      </cons>
    </option>
    <option id="option-b">
      <name>方案 B：普通（非 external content）FTS5 表 + 全粒度索引（`detail` 同样不声明）+ 非 STRICT 表</name>
      <pros>
        schema 最简单，无触发器、无代理主键、无 rowid 绑定问题；
        写路径直白，不依赖数据库触发器的正确性。
      </pros>
      <cons>
        全文内容存两份（documents.content 一份 + FTS 表内一份），叠加 trigram 的 ~3× 索引后
        磁盘占用显著高于方案 A；体积压力更大，因而更容易在将来被诱导去降索引粒度——而那会直接
        废掉 4 字中文查询；

      </cons>

    把 plan 01-01 的 tracer 版 `open()` 扩展为 RESEARCH § Pattern 1 的完整六步序，实现落在新文件
    `src/open.rs`。顺序**不可并行、不可颠倒**：

    1. `std::fs::create_dir_all(db_path.parent())`，然后**先**用 `rusqlite::Connection::open` 打开 writer
       （读写 flags），由它创建 DB 文件。
    2. 在 writer 上执行 `PRAGMA journal_mode=WAL`。必须用 `execute_batch`（或 `query_row`），
       **不能用 `Connection::execute`**——该 pragma 返回一行结果，`execute` 遇到返回行会报
       `ExecuteReturnedResults`。
    3. 同一个 `execute_batch` 里接着设每连接 pragma 套餐：`busy_timeout`（常量 `BUSY_TIMEOUT_MS = 5_000`）、
       `synchronous=NORMAL`、`foreign_keys=ON`。
    4. 校验版本：`SELECT sqlite_version()` 解析为三元组，低于常量 `MIN_SQLITE = (3, 51, 3)` 时返回
       `StoreError::SqliteTooOld`。然后 `migrations().to_latest(&mut writer)`——注意签名要求
       `&mut Connection`，所以**迁移必须在 `Mutex::new(writer)` 之前用裸 Connection 完成**（Pitfall 7）。
    5. **迁移完成之后**才建只读池：`SqliteConnectionManager::file(db_path)`
       `.with_flags(OpenFlags::SQLITE_OPEN_READ_WRITE | OpenFlags::SQLITE_OPEN_URI)`
       `.with_init(...)`，`with_init` 内按序执行 `busy_timeout` → `foreign_keys=ON` → `query_only=ON`
       （`query_only` 必须放最后，此后该连接无法再改任何设置）。池大小取常量
       `READ_POOL_MAX_SIZE = 4`。用读写 flags 而非 `SQLITE_OPEN_READ_ONLY`：只读 flags 的连接在 `-shm`
       缺失时（崩溃后首次打开）无法创建它，会拿到 `SQLITE_CANTOPEN`；读写 flags + `query_only=ON`
       既保留 WAL 恢复能力又保证写被拒。**`query_only` 不暴露任何开关或配置项**（Pitfall 3）。
    6. `pub fn close(self) -> Result<(), StoreError>` 在 writer 上执行 `PRAGMA wal_checkpoint(TRUNCATE)`。

    对外 API 用闭包式（Pattern 2），因为它天然禁止长持有连接、且让「跨 await 持写锁」成为编译错误：
    `pub fn write<T>(&self, f: impl FnOnce(&rusqlite::Transaction) -> Result<T, StoreError>) -> Result<T, StoreError>`
    ——取 `std::sync::Mutex` 锁（用 `unwrap_or_else(|e| e.into_inner())` 处理毒化）、开事务、调闭包、commit；
    `pub fn read<T>(&self, f: impl FnOnce(&rusqlite::Connection) -> Result<T, StoreError>) -> Result<T, StoreError>`
    ——从池取连接、调闭包、连接出作用域即归还。
    **必须是 `std::sync::Mutex` 而不是 `tokio::sync::Mutex`**：前者的 guard 是 `!Send`，把「在 `.await`
    上持有 writer 锁」变成编译错误而不是运行期长事务。
