    `pub fn escape_fts_query(q: &str) -> String`：把整个用户输入包成**一个双引号短语**并把内部的
    双引号加倍。参数绑定只保护 SQL 层，保护不了 FTS5 的查询语法层——`"`、`*`、`^`、`:` 与
    `AND`/`OR`/`NOT` 在 MATCH 串里都有特殊含义，既是功能 bug 也是注入面（Pitfall 6）。

    `pub fn search(conn: &rusqlite::Connection, project_id: &str, q: &str) -> Result<Vec<SearchHit>, StoreError>`
    按 `q.chars().count()` 分流（常量 `MIN_TRIGRAM_CHARS = 3`）：
    - **≥3 字符**：走 trigram MATCH——`SELECT d.id, d.title, d.rel_path FROM documents_fts f
      JOIN documents d ON d.rowid_pk = f.rowid WHERE documents_fts MATCH ?1 AND d.project_id = ?2 ORDER BY rank`，
      第一个参数绑 `escape_fts_query(q)` 的结果。JOIN 条件必须打在 `d.rowid_pk = f.rowid` 上
      （schema v1 用显式整型主键绑 `content_rowid`）。
    - **<3 字符**：走 LIKE 回退，且**打在 `documents` 表而不是 FTS 表上**——
      `SELECT id, title, rel_path FROM documents WHERE project_id = ?1 AND (content LIKE '%'||?2||'%' OR title LIKE '%'||?2||'%')`。
      语义等价、路径更短，且把 FTS 表的 LIKE 索引化能力完整保留为 Phase 2+ 的余地。
      D-02 的成本判断（500 文档规模下全扫远在 300ms 预算内）已在 CONTEXT 中拍板。
    两条分支都用 rusqlite 参数绑定，**禁止 `format!` 拼 SQL**（Security Domain V5）。
    结果映射为 `prism_types::SearchHit`。

    `tests/fts_cjk.rs` 按 `<behavior>` 写全四个测试函数（六组断言集中在第一个函数里）。样本文档照 RESEARCH § Code Examples 的
