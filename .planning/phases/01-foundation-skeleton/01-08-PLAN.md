<objective>
在薄 shell 上打通 A1 要验证的两条 IPC 通路：一条总线事件经粗粒度 Tauri event 往返前端
（notify-then-fetch），一条命令经 `tauri::ipc::Channel` 有序流式返回。

Purpose: Tauri 官方文档明确警告——事件监听器在发射端快速连发时**可能乱序处理**，且事件载荷永远是
JSON 字符串、缺少命令具备的 capability 安全控制；官方建议「有序、高吞吐的数据投递请改用 Channel」。
这就是为什么本项目要两条通路：FS 驱动的引擎主动推送只能走事件（前端没有常驻 channel），
所以事件载荷必须是**粗粒度失效信号**而非业务数据；请求作用域的有序流走 Channel。
把这两条各自验证一次，是本阶段 A1 修正的全部内容。

Output: `bus_adapter`（含 Lagged→Resync）、全部 `#[tauri::command]`、`dev_smoke_stream`、进程内 IPC 测试。
</objective>

    新建 `src-tauri/src/bus_adapter.rs`。**这是全 workspace 中唯一允许 link tauri 的地方之一**
    （另一处是 commands.rs），engine 侧对此一无所知。

    把「收到什么 → 该做什么」抽成一个**纯函数**，这样它可以脱离 tauri 运行时被单测：
    `pub enum BusOutcome { Emit(EngineEvent), Resync, Stop }`，
    `pub fn map_recv(r: Result<EngineEvent, tokio::sync::broadcast::error::RecvError>) -> BusOutcome`。
    三条映射：`Ok(ev) => Emit(ev)`；`Err(Lagged(_)) => Resync`；`Err(Closed) => Stop`。

    `Lagged` 分支不是可选的。`tokio::sync::broadcast` 用有界环形缓冲，接收端落后时会**丢弃最旧消息**
    并返回 `RecvError::Lagged(n)`。因为载荷是粗粒度失效信号，丢消息可以用一次 `Resync`（全量失效）
    无损补偿；若走 push-payload 则丢的是不可恢复的业务数据——这正是 notify-then-fetch 相对
    push-payload 的全部价值所在。**漏掉这个分支的表现是前端静默停留在旧数据上，不报任何错。**

    `pub fn spawn(app: tauri::AppHandle, mut rx: broadcast::Receiver<EngineEvent>)`：
    在 `tauri::async_runtime::spawn` 里循环 `rx.recv().await`，把结果喂给 `map_recv`，
    按 `BusOutcome` 分别 `app.emit(EVENT_CHANGED, ev)` / `app.emit(EVENT_CHANGED, EngineEvent::Resync)` / `break`。
    发射失败只记 `tracing::warn!` 不中断循环（窗口已关是正常情况）。
    常量 `EVENT_CHANGED = "prism://changed"`。

    在 `src/lib.rs` 的 setup 中：构造 Engine 后 `bus_adapter::spawn(app.handle().clone(), engine.subscribe())`，
    并调用 `engine.init_secrets()`（失败只 warn，**不阻断启动**——D-06 要求无 key 时应用照常启动）。
    `src-tauri/Cargo.toml` 若尚缺 `tokio` 的 `sync` feature 与 `tracing`，在此补齐。
