## 1. 重述与现行 BRD/PRD 的差异分析

把重述拆成三个 job,对照现有文档集:

| Job | 现有覆盖 | 缺口 |
|---|---|---|
| J1 集中管理并理解多项目的 AI 文档 | F1(导入同步)+ F2′(速读区)+ Inbox,**基本覆盖** | 现有信息架构是「项目切换器」范式,Workspace 只是壳;「集中」意味着 Inbox 与搜索应默认跨项目聚合(小改) |
| J2 评论/反馈让 LLM 开发透明 | F3 + F4 + REQ-4.7 溯源,**完全覆盖** | 「透明」叙事下,溯源(谁改的、因什么改的)从辅助功能升为卖点之一,无需改设计 |
| J3 LLM Wiki:跨项目引用 + server/client 防偏差 | **完全未覆盖**。现有对象模型中 Document/评论/引用全部锁在单 Project 内;卡片仅有 Workspace 级倾向(F5 OQ-5.2);「入库冲突检测」在 P1 池但仅指单项目内新素材与决策卡矛盾 | 需要新能力(本文暂编号 **F8 跨项目知识层**):跨项目引用、契约订阅、漂移检测、漂移→闭环 |

**重心变化判断**:原 BRD 的护城河排序是「双层双语 > 理解留存 > 评论回流 > 剪藏」。重述把重心移到「多项目知识层 + 透明闭环」——与 MVP′(Lens 降级为速读区)的方向一致,并新增了第二条不依赖双语的护城河:**Workspace 级知识图 + 漂移驱动闭环**。原第一护城河(双语双层)退为增强项,与 §3.5 回归条件不冲突。

## 2. 外部调研:跨仓库上下文的 2026 生态

### 2.1 三个层面的现状

**企业级(code-graph + CI,团队定价)**:跨仓上下文已被确认为 agent 规模化的头部问题。Riftmap 报告的行业数据:上下文漂移占 agent 失败原因约 40%,Mabl 用 850 行「Repo Coordination Graph」把它降到 5% 以下;Meta 的跨仓依赖索引把「什么依赖 X」从 ~6000 token 的多文件探索压到 ~200 token 的图查询。Qodo 等评审工具主打跨仓下游影响检测。GitHub 社区有 Copilot 跨仓上下文(Web ↔ Microservice)的功能请求——需求真实且未被平台满足。**共同点:面向团队/企业,以代码依赖图为中心,不做文档理解层,无个人可用形态。**

**个人/小团队(手工 meta-repo 模式)**:实践者自建「agents 元仓库」——AGENTS.md 仓库映射 + repos.yaml + conventions/ + workflows/ + active-work/ 跨会话记忆,agent 开工先读元仓库。作者自认的局限:**文档漂移风险真实存在、需要人工维护**。这正是可产品化的空隙:PrismDocs 的 watcher + 锚定引擎能把「人工维护、漂移靠自觉」变成「自动监听、漂移自动警示、修复走闭环」。

**代码级契约工具(OpenAPI/codegen/contract testing)**:server/client 同步的成熟解法是 IDL 单一真相源 + 代码生成(OpenAPI + Orval 等)+ 契约测试。**边界清晰:它们管「类型和端点对不对」,不管「决策、行为约定、架构文档对不对」**;需要 CI 与工程纪律,恰是 vibe coder 缺的;且大量真实偏差发生在没有 IDL 的层面(业务规则、错误处理约定、架构决策)。互补而非竞争——PrismDocs 甚至可以把 openapi.yaml 当作一份「契约文档」纳入订阅。

### 2.2 空白判断(更新 BRD §3.2)

「**个人级、文档层、带评论闭环的跨仓一致性**」无人占位:markupmarkdown/Plannotator 单文档单仓;CoWiki 团队知识沉淀、无 repo 绑定、无编码 agent 闭环;DeepWiki/Google Code Wiki 单仓只读生成;企业跨仓工具无文档理解层、无个人形态;OKF 是单 bundle 格式,跨 bundle 引用无定义、链接无类型(社区批评原文)——**类型化跨项目链接恰好是 PrismDocs 可以在 OKF 之上补齐的语义层**,与「OKF 之上的人类理解与决策层」定位语自洽。

**常见反驳与回应**:「用 monorepo 就行」——现实中部署边界、模板脚手架、历史原因让多仓是常态,且编码 agent 天然按仓工作(每仓独立 CLAUDE.md/会话);meta-repo 模式的流行本身就是 monorepo 不可行时的证据。

## 3. F8 跨项目知识层:能力设计

设计基线:**全部复用既有引擎**(F1 多项目 watch、锚定引擎、F4 闭环、Inbox),F8 是组合而非新引擎;不污染源文件原则不变(引用关系存 sidecar)。

### 3.1 对象模型扩展

- Workspace 升级为真实容器:跨项目搜索、跨项目 Inbox 聚合(J1)。
- 新增 `xref` 表:`src(project_id, doc_id, block_id?)` → `target(project_id, doc_id, block_id?)`,`link_type ∈ references | depends-on | contract-of`(受控小词表,吸取 OKF「链接无类型」教训),`created_by(user | auto-detected)`,`confidence`。
- Block 级引用直接复用锚定引擎的 Block ID 与迁移机制——上游文档被 agent 重写后,跨项目引用与订阅随锚点迁移,置信度低时显式降级警示(与评论同一套「0 静默丢失」契约)。

### 3.2 引用的四种建立方式

1. **应用内显式建链**(P0):文档/Block 上「引用其他项目文档」动作;
2. **卡片双链跨项目化**(P0,小改):`[[` 联想候选扩展到全 Workspace(落实 F5 OQ-5.2 的倾向);
3. **自动发现**(P0.5):文档正文中已有的相对路径/repo URL 链接若解析到另一已导入项目的文件,提示「识别为跨项目引用,确认?」;
4. **frontmatter `resource` 字段**(P1):OKF 标准字段承载跨项目引用,导出时天然合规。

### 3.3 契约文档与订阅(防偏差的核心机制)

- 任一文档可标记为 **Contract**(受控 type 词表已有 `Spec`,增加 contract 标志位或 `type: Contract`,进设置词表登记);典型:API spec、数据模型、协议约定、共享业务规则。openapi.yaml/proto 等非 Markdown 契约以附件级纳入(变更监听 + 文件级订阅,不做 Block 级)。
- 下游项目**显式订阅**契约文档,粒度可到 Block(如只订阅 `### POST /orders` 一节)。订阅制是警报疲劳的第一道闸:**只有订阅命中的变更才产生跨项目警示**。

### 3.4 漂移检测 → 闭环(F8 的价值闭合点)

MVP 只做**结构信号**,不做语义比对:

1. 上游契约文档变更 → F1 watcher + 锚定引擎 Block 级 diff(一次计算三用途的第四个消费方);
2. 命中被订阅 Block → 下游项目 Inbox 出现「上游契约变更」事项:上游 diff 摘录 + 变更来源(复用 REQ-4.7 溯源:哪个 agent/Bundle 触发的上游变更)+ 受影响的下游引用方清单;
3. **一键「生成下游核对反馈」**:在下游项目生成一个 Feedback Bundle,内容 = 上游变更 diff 摘录 + 指令头(「上游契约 X 节已变更,核对本项目文档与实现是否需要跟进,逐条回执」)→ 走既有 F4 三信号回收与复核。**漂移修复完全复用评论闭环,agent 侧零新协议**;
4. 用户复核 resolve → 计入北极星闭环(跨项目闭环是闭环的一种)。

**P1 增强**:语义漂移检测(LLM 比对上下游文档断言矛盾,即「入库冲突检测」的跨项目版);双向流(下游想改契约 → 在上游契约文档上发起评论)MVP 已天然支持(评论本就可写在任何项目的文档上)。

### 3.5 Agent 侧消费

- **Context Pack 升级为 Workspace 作用域**(F7 小改):组装器可勾选其他项目的文档;典型用法:client 项目的 Pack 里带上 server 的 api-spec.md;
- CLAUDE.md 协议片段追加一句:「本项目的上游契约由 PrismDocs 管理,开工前拉取指定 Context Pack」;
- MCP 新工具 `list_dependencies(path)` / `get_upstream_contracts()` 列 **P1**(MVP 用 Context Pack 承载已足够)。

### 3.6 OKF 对齐

跨项目引用在导出 OKF Bundle 时重写为 bundle 间相对链接或 `resource` 字段;`link_type` 导出为扩展字段 `x-link-type`。Workspace 导出 = bundle-of-bundles,每项目一个 bundle——对 OKF「无跨 bundle 语义」的批评给出产品级答案,强化「OKF 之上的理解与决策层」定位。

## 4. 对功能优先级的影响(建议,待拍板)

| 功能 | 建议 | 理由 |
|---|---|---|
| F1/F2′/F3/F4 | 不变,仍是关键路径 | J1/J2 的载体;F8 全部构建其上 |
| **F8-lite 进 MVP″** | 显式建链 + 契约订阅 + 结构漂移 Inbox + 一键下游反馈 | 重述的第三 job;工程量小(≈1–1.5 周:xref 表 + 订阅 UI + 命中路由 + Bundle 模板),因为四个依赖引擎全是现成的 |
| F7 Context Pack | 保留,升级 Workspace 作用域 | 跨项目上下文的交付通道 |
| F5 卡片 | 保留,双链跨项目化 | 「理解」由速读区 + 卡片共同承担;Workspace 级卡片顺势落实 |
| **F6 剪藏** | **建议降为 P1** | 重述三个 job 均未涉及外部网页素材;它是唯一可完整剥离的功能,且占独立工程线(扩展 + 桥接)。代价:BRD M3 的商店引流入口延后——**需创始人确认**,若引流权重高可保留并行开发(它本不占关键路径) |
| 全文 Lens | 维持 P1(回归条件不变) | 见《调研_技术基建与开发Phase》§3.5 |

**修订后 MVP″ = F1 + F2′(速读区)+ F3 + F4 + F8-lite + F7(Workspace 级)+ F5**,F6 与全文 Lens 为 P1。

**Phase 影响**(对《调研_技术基建与开发Phase》v0.2 的 Phase 表):关键路径 1→2→3→5→6 不变;**Phase 7 改为「F5 + F7(Workspace 级)+ F8-lite」**;Phase 8(F6 扩展)移出 MVP 或按引流决策保留并行;锚定引擎(Phase 3)的输出接口冻结时把「跨项目订阅命中」列为第四消费方。

## 5. 整体构想 v2(一页纸)

> **PrismDocs 是 vibe coder 的多项目工程知识工作台**:集中管理 Claude Code / Codex 等编码 agent 在各个仓库生成的文档,用中文速读区 + 段落级评论让 LLM 开发**看得懂、批得动、可追溯**;评论结构化回流驱动 agent 迭代;项目间文档相互引用、契约可订阅——上游(如 server 的 API spec)变更时,下游(如 client)自动收到核对警示并一键生成修复反馈,让独立开发的项目不产生偏差。数据层兼容 OKF,知识库无锁定。

- **北极星不变**:闭环数/周(跨项目闭环计入)。
- **新增护航指标**:漂移警示处理率(resolve/忽略比)、漂移警示误报率(<10%,靠订阅制控制)、跨项目引用数/Workspace(采用度)。
- **叙事顺序调整**:对外主打「透明的多项目 AI 开发」(J1+J2+J3),双语理解层作为东亚市场的增强叙事而非第一卖点。

## 6. 新增假设与 M0 增补

| 假设 | 验证方式(并入 M0) |
|---|---|
| 目标用户确实多仓开发(≥2 个相互关联 repo) | 走查招募筛选题 + 访谈「你现在怎么保持 server/client 文档一致?」 |
